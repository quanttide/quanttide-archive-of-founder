# 意图系统 — 设计洞察

> 记录设计意图系统过程中的关键认知转折，供未来回顾。

---

## 1. 原型做错了什么

第一个 HTML 原型是"选意图"的。三个按钮，点一个锁定，其他禁用。表面看起来合理——"你选了立场就不能反悔"。

但粟裕在豫东战役里改了四次意图。现实中的指挥官不是做一次选择就锁死的。

更根本的问题是：**玩家点按钮选意图这个交互本身就不对。** 指挥官不会坐在指挥所里说"让我选一下我的意图是什么"。他面对的是情报，他做判断，判断中自然包含立场。意图应该是判断的副产品，不是操作入口。

这是原型阶段最大的认知转折：不要把意图做成选择题，要做成系统对玩家判断的反馈。

## 2. "切换有代价"想对了，但想浅了

"意图可切换，切换消耗 +1"是对的——改变决心确实有成本。但原型里的消耗只是一个抽象数字。

消耗不应该是"扣点数"，它应该体现在游戏世界的具体变化里：切换意图后，时间推进了一格；部队刚准备出发又要停下来等新命令；正在传递中的旧情报可能在切换后失去价值。

**抽象消耗和具体消耗的区别，就是"游戏机制"和"模拟现实"的区别。**

## 3. "锁定"像一个约定俗成的设计陷阱

QA 文档最初写的是"意图按钮锁定不可改"，我照抄了，没有质疑。回头看，这是从传统策略游戏的"选择不可逆"习惯里带出来的——技能树点了不能洗、外交选项选了不能改。但指挥官决策游戏要模拟的是人在不确定中做决定，不是人在菜单里做配置。

被纠正后才意识到：好的设计约束不是"你不能改"，而是"你可以改，但你要承担改的后果"。

## 4. 战役预设初始意图是对的，但不够

每个战役开局指定一个初始意图（帝丘店→积极防御，开封→保护平民），这个做法的核心洞察是：**指挥官到任的时候，战场已经告诉他该做什么了。**

但现在的原型只是把初始意图作为一个默认值写在 JSON 里，玩家看到的是标签高亮了，没有让玩家感受到"这个局势在推着我往这个方向走"。

理想的做法应该是：开局展示情报和局势（不展示意图标签），玩家通过做第一个决策来表达意图，系统再反馈"你的决策表明你的意图是积极防御"。这样意图是玩家自己"长出来的"，不是系统预设的。

## 5. 这个系统应该多晚才算完成

意图系统不是独立的——它必须等情报系统（Phase 2.1）上线后才能体现价值。没有情报迷雾，玩家直接能看到战场全貌，意图就是个多余的标签选择器。有了情报迷雾，玩家面对不确定的信息做出判断，这个判断投射为意图才有分量。

这也是为什么 Phase 2 先做情报系统再做意图系统——不是编码顺序问题，是**设计上意图依赖情报才成立**。

## 6. 设计文档分层的价值

这次做完 intent 系统后同步创建了 `docs/intention/`（概念层）和 `docs/brochure/`（玩家层），并明确了分层纪律。

回头看，如果没有这个区分，intention 里写的理想设计就会被当作"现状"或"已实现功能"被误引用。brochure 里的玩家说明也会被当作设计规范来要求实现。分层不是形式主义——它防止了"文档描述的状态和实际代码状态脱节"这个之前踩过的坑。

## 7. LLM 验证揭示了映射规则的边界

用 Python 脚本调用 LLM 模拟指挥官判断，9 个场景 7/9 匹配预设意图。

三个基准场景（帝丘店、开封、豫东第一阶段）全部匹配，验证了"情报→判断→意图"映射规则的基础成立。

两个不匹配案例暴露了更有价值的信息：

**矛盾情报场景**（预设为"积极防御"）：
LLM 选了"收集情报"——理由是两份情报互相矛盾，贸然防御可能分散兵力，先核实再说。这个判断比预设更合理。

**多重压力抉择场景**（预设为"积极防御"）：
LLM 同样选了"收集情报"——理由是侦察兵失联、敌主力位置不明，贸然分兵可能中计。

共同规律：**当 LLM 认为信息不足以支持决策时，它倾向于退回"收集情报"作为默认退路。** 这不是映射规则错误，而是暴露了预设意图的盲区——预设意图假设玩家在已知信息下做最优选择，但"信息本身是否足够做决策"这个前提没有被预设意图机制考虑。

这对设计的启示是：**意图系统不应该只有正向映射（情报→意图），还应该有一条反向保护规则：当情报质量低于阈值时，默认意图应该是"收集情报"而非保持原预设。**

这也印证了第 5 条的结论——意图依赖情报才成立。没有可靠的情报，任何意图都是空中楼阁。

## 9. Phase B 参谋长原型实验的认知转折

> 构建参谋长模式交互原型（5 场景：2 基准 + 2 误导 + 1 矛盾）的过程中，验证了设计假设，也揭开了几个之前没意识到的深层问题。

### 9.1 两种模式对应两种"认知加载"节奏

这不是 UI 上的区别。两种模式的信息排列顺序决定了玩家如何理解"自己在做什么"：

**极简模式（Phase A 原型）**：
```
先给答案（意图标签）→ 再看理由（行动选项）
```
玩家先选定立场，系统基于立场展示可用选项。认知路径是"我要做什么→我能做什么"。

**参谋长模式（Phase B 原型）**：
```
先给事实（情报）→ 再给分析（参谋长）→ 做决定（行动）→ 看到立场（意图反馈）
```
认知节奏是"世界是怎么样的→别人怎么看→我怎么看→我的立场是什么"。

关键区别：**前者假定了玩家已经知道自己的立场，后者不假定。** 如果指挥官决策游戏的目标受众是"不确定该怎么做的玩家"，参谋长模式天然匹配。但如果目标受众是"已经知道自己要做什么的策略玩家"，极简模式更有效率。

这不是优劣问题，是受众定位问题。

### 9.2 参谋长的"错误建议"才是这个验证实验的核心价值

Phase A 的 LLM 验证（3/3 匹配）只证明了"情报→意图映射成立"，但这个验证忽略了最关键的命题——**参谋长什么时候错？**

误导场景中的发现：

- **假目标场景**：侦察兵报告"看到大量坦克"，参谋长判断"邱清泉战车连已至"→建议构筑防坦克阵地。实际是木制模型。参谋长的分析从情报角度看完全合理，但结论是错的。
- **假撤退场景**：情报称"敌军向西撤退"，参谋长判断"可能是战术转移"→建议先侦察不追击。实际敌在迂回包抄。参谋长的谨慎从情报角度看是对的，但错过了打破包围圈的时机。

关键认知是：**参谋长不是故意误导玩家的反派。他是和玩家站在同一信息基础上、用同样逻辑推理但得出错误判断的参谋军官。** 这才是真实指挥所的样子——指挥官和参谋共享同一份情报，但可能得出不同判断。

这也揭示了"参谋长模式"和"提示系统"的本质区别：提示系统总是给出正确答案（或者玩家知道它是正确答案），而参谋长的建议可能错。正因为可能错，玩家才有做判断的空间。

### 9.3 "系统分析你的意图"的马后炮问题

原型实现了"从决策推断意图"的循环：
```
情报 → 参谋长分析 → 玩家点行动按钮 → 系统推断意图 → 反馈给玩家
```

实现过程中发现：如果系统从玩家的决策行为中推断意图（"你点了构筑工事→你的意图是积极防御"），意图标签本质上是**马后炮**。玩家点按钮时已经知道自己要做什么了，不需要系统告诉他"你的意图是积极防御"。

但后来厘清了一个关键区别：**"系统分析玩家意图"和"参谋长理解指挥官意图"是两回事。**

- ❌ **系统分析玩家意图**：对玩家说"你的意图是积极防御"——马后炮，玩家不需要被告诉
- ✅ **参谋长理解指挥官意图**：参谋长观察指挥官的行动，理解其意图，然后基于这个理解去调配兵棋系统资源——这才是对话，不是注释

为什么后者不是马后炮？因为参谋长需要**根据对指挥官意图的理解来工作**：他需要知道指挥官的意图才能判断应该调哪支部队、优先传递哪些情报、作战方案应该在哪个方向上展开。这个理解的过程产生了实际价值——**参谋长把指挥官不可言说的"判断"翻译成了兵棋系统可以执行的"操作指令"**。

这也揭示了意图系统的真正定位：**意图不是给玩家看的，是给参谋长看的。** 玩家通过决策表达意图，参谋长理解意图后帮助玩家操作兵棋系统。玩家不直接操作兵棋引擎，他通过参谋长来指挥部队。

### 9.4 原型暴露的最大缺陷：玩家无法忽略参谋长

五个场景的布局中，玩家必须先看参谋长分析才能点行动按钮。这个强制流程隐含着"参谋长说的有参考价值"的暗示——在真实指挥所中并非如此，指挥官可以不听、打断、或者照着相反方向决策。

好的设计应该让情报本身是充分的——**不看参谋长分析也能做出充分决策**。参谋长只是一个额外层。如果玩家说"我不看参谋长的废话"，他应该照样能玩。

这一点在原型中没有做到，需要在 Phase C 实现时修正：情报面板和行动面板之间的链接应该是完备的，参谋长分析框是附加层，不是必经层。

### 9.5 意图的真正消费者是参谋长，不是玩家

实验做了一圈，7 维度对比表列了一遍，最后发现一个更根本的答案：

**意图不是给玩家看的，是给参谋长看的。**

- 玩家通过决策表达意图（点行动按钮 = 说"我的判断是这样的"）
- 参谋长接收意图，理解为"指挥官想往这个方向走"
- 参谋长基于这个理解，调配兵棋系统资源（调部队、选情报、出方案）
- 兵棋系统执行作战方案

整个链路是：
```
玩家做决策 → 参谋长理解意图 → 参谋长操作兵棋系统 → 兵棋系统执行
```

这个定位解决了第 2 节的"抽象消耗"问题——参谋长操作兵棋系统时，消耗是真实发生的。他需要时间传递命令、调整部署、等待情报延时。

这个定位也解决了 9.4 的"玩家无法忽略参谋长"问题——参谋长不是提示系统，他是玩家和兵棋引擎之间的接口。玩家可以自己操作兵棋引擎（极简模式），也可以委托参谋长操作（参谋长模式）。两种模式不冲突，玩家选哪种取决于他想在哪个粒度上指挥。

真正的 B3 评审问题应该是：**玩家和兵棋引擎之间，要不要设参谋长这一层？** 而不是"哪种交互模式好"。

### 9.6 参谋长 = LLM，智商有限天然成立

确定参谋长角色就是 LLM 后，上面 5 个"不对的东西"第 1 条（参谋长是一个人不是一个机构）有了新视野：

- ❌ 需要设计"参谋长会犯错"的机制？不需要。**LLM 的有限智商本身就是天然的沉浸感来源。** 它可能遗漏关键情报、被误导信息带偏、做出不符合战役逻辑的建议。这些不是需要特意写的 bug，是 LLM 的自然行为。
- ❌ 需要设计"参谋长可能误解指挥官意图"的反馈？也不需要。LLM 本身就会误解。它读了指挥官的决策文本后，输出"参谋部理解您的意图是..."——这个理解可能对可能错，错的时候就是真实指挥所的"复述确认"环节。
- ❌ 不需要管理参谋长的状态、疲劳、派系。这些复杂度在 LLM 的上下文限制和推理能力限制中天然存在。

这个视角颠覆了 Phase A 的一个认知。当时做 LLM 验证实验（第 8 节）关注的是"LLM 是否能正确推断意图"，但那个问题不重要——**LLM 推断错了更有意思**。玩家发现"参谋长理解错了"然后纠正他，这个互动比"参谋长永远正确"有价值得多。

所以实现上应该反过来：**不要追求参谋长理解的准确率，要在意的是当参谋长理解错了，对话界面是否允许指挥官纠正。** 纠正这个过程——"不是，我是要打援不是防御"——才是参谋长模式不可替代的东西。

## 8. LLM 实验对游戏设计意图的帮助

这个实验的价值不在"验证结果正确"，而在验证过程本身揭示了几个设计方向。

实验用的 LLM 扮演的角色是**参谋长**——他分析情报、给出建议，但不做决策。玩家是指挥官，是最终的意图澄清和决策者。两者角色清晰分离。

**8.1 确认了"情报→建议"的映射是自然的**

LLM 不需要规则表、映射表，仅凭情报文本就能输出判断和建议。这意味着游戏中参谋长的判断不依赖硬编码规则——只要情报文本写到位，参谋长的分析自然成立。

这对开发的影响是：**不需要为每个战役手写"情报→建议"的映射规则。** 情报文本写到位了，参谋长的分析自然成立。

**8.2 暴露了"预设初始建议"的局限**

两个不匹配案例的共同点是"情报质量低→LLM 退回收集情报"。对应的游戏设计问题是：

如果帝丘店开局给的情报是模糊的、矛盾的，参谋长却建议"积极防御"，指挥官会觉得这个建议不靠谱——情报都互相矛盾，你还让我打？

结论是：**参谋长的建议应该是情报质量的产物，不是 campaign.json 里写死的默认值。** 情报清晰时建议符合战役逻辑，情报模糊时应该建议"先收集情报"。

**8.3 改变了"初始建议"的实现思路**

修改前：
```
campaign.json 写 initial_intent: "defend"
→ 玩家开局看到高亮标签
```

修改后：
```
情报系统输出 → 参谋长根据情报给出建议 → 指挥官看到建议，自己做决定
```

参谋长的建议不是权威，它可能对也可能错。当情报误导时，参谋长也会犯错——这正是指挥官（玩家）发挥判断力的空间。

**8.4 实验中 LLM 的定位澄清**

实验中 LLM 的角色经历过三次修正：

1. ❌ **"模拟指挥官"**——它能做决策，但玩家才是决策者，不对
2. ❌ **"完美指挥官"**——它替玩家做决策，不对
3. ✅ **"参谋长"**——分析情报、给出建议，但不做决策。决策权在指挥官（玩家）手里

这个定位的关键区别是：**参谋长不是系统在给出正确答案，而是参谋军官在分享他的专业分析。** 他的分析有价值但不是命令。当有多个参谋军官时，他们甚至可能给出互相矛盾的分析——指挥官需要在多个建议中做出自己的判断。

这也揭示了游戏不应做的事：不要把参谋长的判断做成"提示系统"或"辅助决策工具"，它应该是世界的一部分——指挥所里除了指挥官还有参谋。

**8.5 实验告诉我们做什么和不做什么**

- **不要做**：意图选择器（"请选你的立场"），把决策变成选标签
- **要做**：情报系统 + 参谋长分析（"根据当前战况，参谋部的判断是..."），让指挥官在情报和建议下自己做最终决定
