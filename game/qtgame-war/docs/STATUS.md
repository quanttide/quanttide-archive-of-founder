# 现状与差距

游戏架构定位：兵棋推演引擎作为底层，指挥官决策系统作为上层，两层面合一。

当前代码仅实现兵棋推演引擎（执行层），指挥官层（战术层）尚未搭建。以下逐项列出差距。

## 1. 战役模型通用性 — Campaign 硬编码

**现状**

`Campaign` 类的字段是帝丘店专属的：
- `huayePower` — 数值命名自带战役上下文
- `fortStrength` — 只适用于"攻核心"类胜利条件
- 援军标记 `qiu_arrived`、`hu_arrived` — 援军名字写死在模型里

**问题**

换一个战役（如汝南、徐东、碾庄）就要改模型类定义，加新字段。本应只改 JSON 配置就完成的事，需要改 Dart 代码。

**原因**

`Campaign` 在设计时被当作"这个战役的全局状态"，而不是"战役的通用状态容器"。通用状态（战力、时间、阶段标记）和战役特定状态（帝丘店防御强度、邱清泉援军）没有分离。

## 2. 缺少"命令"对象 — 指挥官和兵棋之间无协议

**现状**

`GameController` 直接操作棋子：选单位 → 算范围 → 移动/攻击 → 结算。和传统战棋游戏一样，没有"命令"这个抽象层。

**设计要求的**

指挥官层的交互是：
```
判断情报 → 定意图 → 下命令（"第3纵队向曹庄推进，控制渡口"）
     ↓
命令翻译 → 兵棋引擎执行 → 结果反馈
     ↓
收到战报 → 决策下一步
```

**差距**

缺少一个 `Command` 类型和 `CommandExecutor`，负责把抽象命令翻译成兵棋引擎能执行的操作序列。没有这个层，指挥官界面就永远是"点击棋子"而不是"下命令"。

## 3. 回合结构与指挥官时间观冲突

**现状**

```
玩家阶段（我方所有操作）→ AI 阶段（敌方所有操作）→ 下一回合
```

这是经典战棋回合制。但指挥官体验的时间结构应该是：

```
我下达命令 → 时间流逝 → 收到阶段性战报 → 新情报更新 → 做下一个决定
```

**问题**

- 现行回合制把所有操作集中在一个阶段完成，指挥官没有"发出命令后等待"的体验
- 一条命令（如"拂晓前占领渡口"）可能跨越多个执行回合，现有模型不支持长命令持续执行
- AI 阶段是批量处理，不是与玩家命令并行的时间推进

**现状反映**

当前回合结构是为兵棋推演设计的，没有为指挥官体验做调整。

## 4. 情报系统缺失

**现状**

只有 `revealed: bool` — 单位是否对玩家可见。棋类游戏的"战争迷雾"语义：
- 己方单位默认可见
- 敌方单位被侦察过或进入视野后可见
- 战斗中暴露后可见

**设计要求的**

情报需要三个维度：
- **时效性**：这条情报是什么时候获取的？5 小时前还是 30 分钟前？
- **可信度**：来源可靠吗？是侦察兵亲眼所见还是俘虏供述？
- **多层真实**：兵棋引擎知道世界真实状态（上帝视角），指挥官层只能看到情报面板（据报）。两者之间有一层"情报过滤器"。

**差距**

- 没有 `Intel` 类型（时效、可信度、来源）
- 没有情报生成器（真实状态 → 情报过滤 → 指挥官看到的）
- 没有"请求侦察 → 延迟反馈 → 仍滞后于真实"的机制（QA C04 设计要求）

## 5. 指挥风格／意图系统未搭建

**现状**

没有任何意图系统。所有行动对所有玩家始终可用。

**设计要求的**

QA C01 要求：
- 意图可随时切换，每次切换消耗时间/资源
- 行动选项随意图变化，不是同一套按钮加不同修饰
- 禁止选项是直接消失，不是灰掉

PRD 描述：
> "一个决心保护平民的指挥官，不会看到'无差别火力覆盖'的按钮。不是它被灰掉了，而是它根本不在你的决策空间里。"

**差距**

缺少 `Intention` 类型、意图过滤器、意图对叙事层的影响机制。目前所有代码都假设玩家是全知的兵棋推演者。

## 6. 多维度后果系统未实现

**现状**

只有一条后果线：`huayePower` 增减。UI 中的 `Dispatch` 日志只是文本记录，没有独立的状态面板。

**设计要求的**

QA C05 要求三条后果线同时更新：
- 军事态势（相持/交火中/优势/溃败）
- 己方消耗（体力数值，色阶变化）
- 政治影响（国际关注/民意/舆论）

**差距**

- 只有数值增减（huayePower），没有状态机（态势、影响）
- 颜色和图标没有与后果状态绑定
- UI 只有日志列表，没有三条独立后果面板

## 7. 战役配置化不完整

**现状**

| 已配置 | 未配置 |
|--------|--------|
| 地形坐标 | 地形属性（移动消耗、防御加成） |
| 兵种属性 | 胜利条件判定规则 |
| 单位初始部署 | 阵营中文名 |
| 援军触发（回合数） | UI 配色和文案 |
| | 战力阈值（hitMod/moveMod 的 if-else 链） |

**问题**

地形属性、战力阈值、胜利条件都是战役相关的，但都写在代码里。换战役时这些逻辑也必须同步修改，违背了 JSON 配置的本意。

## 8. 文档与代码不同步

| 文档 | 描述状态 | 代码实现 | 差距 |
|------|---------|---------|------|
| `docs/prd/index.md` | 信息迷雾、意图驱动、不可逆决策 | 经典战棋，无迷雾无意图 | 设计做了一半就停下 |
| `docs/spec/war.md` | 战术层/执行层严格隔离 | 两层混在 Game+GameController | 架构未落地 |
| `docs/ixd/headquarters/index.md` | 三栏桌面布局、签署命令锁定全局 | Flutter 默认布局 + 战斗视图 | 交互设计未编码 |
| `docs/qa/index.md` | 8 个验收场景 (C01-C08) | 全部未实现 | QA 无法执行 |
| `docs/add/domain.md` | 战役配置驱动、通用模型 | Campaign 硬编码 | 模型承诺未兑现 |

---

## 总结

当前代码是一个**可运行的兵棋推演引擎**，能跑帝丘店战役的简版。但要变成"指挥官决策游戏"，需要在现有引擎上叠加一个新层面。最快路径不是重写，而是**在兵棋引擎和 UI 之间插入指挥官层**。
