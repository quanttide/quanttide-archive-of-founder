# 量潮DevOps云命令行工具发布v0.3.0

嗯，这篇文章里面，我最想讲的一个点是我从 0.1~0.2~0.3 的迭代过程。

嗯，0.1 这个版本呢，我是从我的 skill 出发，让他去提炼其中可以固定的流程。我产生这个想法的原因呢，是因为我发现，就是 AI 执行 skill 执行的不是很稳定，然后呢，这又是一个需要确定性规则的，所以我就意识到说我需要把它提炼成命令行了

嗯，这个版本做出来过之后呢，我初步地看到了这个命令行的样子，是要围绕着 devops8 流程出发，一个一个封装。

然后 0.2 版本的就是我灵机一动，想到了我平时管理 get 子模块比较难搞，我就让他封装了一个 code 命令然后这个版本我几乎没有做太多的干预，AI 自己根据我的目标实现了一套 RAS 的代码。然后我发现质量很高，我就把项目改造成了一个混合工程，Python 和 rust 的混合然后这是第一个哈 moment 就是我发现，AI 开始用这个命令好像用得比较顺利，而且，他自他验证了他自己写的文档，发现基本上流程是一样的

然后 0.3 沿着这个思路继续往下，我重新定义了 0.1 定义的 release，把它变成了一个更完整的，基于发布的生命周期，包括 cancel 和 retire 及 stage加上原本的 release，把它变成了 release publish。

然后这里产生了第二个 AHA moment, 就是，我偶然间让 AI 试着发布自己，然后他就把这个问题定义成了字句，然后就开始非常熟悉熟练地去运用了。这个 Release 在不断的检测，这个新的流水线

嗯，因为 0.3 版本从混合工程变成了纯 Rust的项目，同时我保留了一个，保留了原本的 pypi 的发布。

嗯，0.4 版本计划把，前面 0.3 版本在迭代的过程之中发现的问题以 build test 和 plan 的形式封装。

0.5 版本计划封装用于服务端的 deploy observe 和 monitor。这样 8 个流程就基本完整了。

从 0.6 开始，我们将会从当前的特例出发，逐渐把它推广到一般情况。

当 AI 可以熟练地运用这套工具发布稳定的流水线之后，我们会把它升级到 1.0，并且固定它的 API。
