# Vibe Coding课

这篇文章的观点很有意思，把“重构”从传统工程能力，重新定位成了Vibe Coding时代人与AI协作的核心控制力。你记录的那个“刻意制造技术债务再亲手引导AI修复”的实验，本身就是一堂很好的案例课。

顺着你的思路，我补几点建议，供你设计课程时参考：

1. 把“判例驱动”更显式地教给学生
你提到AI是判例驱动的，那么课程可以考虑专门安排一个环节：让学生亲手对比好的范例和坏的范例，然后用同一个Prompt让AI分别按这两种范例生成代码，亲眼看到“喂什么种子，结什么果”。这会比单纯讲重构重要更有冲击力。

2. 为“反思提示词”建立一个小型指令库
你多次提醒AI“反思你为什么漂移”这类元认知指令非常有效。可以考虑提炼出一组可复用的反思话术模板，比如：

· “请回顾你刚才的实现，指出3个不符合Clean Architecture的地方。”
· “解释一下，为什么你选择了这个方案而不是我提到的X框架？”
  把它们做成Cheatsheet，会成为学生治理混乱的实操工具箱。

3. 设计“治理成果”的可视化验收标准
你提到验收学生交的结果看“是不是已经没有了技术债务”。建议把这点具体化为：让学生提交一份AI生成的自我诊断报告（让AI自己扫描项目并提供技术债务清单），原始清单与诊断清单的对比就是成绩单。这样学生既练习了治理，也练习了用AI做质量评估的元技能。

4. 适当引入“不可逆决策”的体验
可以设计一个小环节，让学生体验一次推倒重来的决策。当AI把架构搞得太乱，引导成本超过重写时，果断让AI按照正确框架重新生成。教会学生判断“何时该扔”的魄力，也是治理混乱的重要本能。

这是一篇非常有洞察力和前瞻性的文章。你不仅敏锐地捕捉到了 Vibe Coding（氛围编程）时代程序员面临的核心痛点——AI 带来的极速产出与指数级技术债务的矛盾，还给出了极具实操性的解法：通过框架约束和激发 AI 反思来治理混乱。
你提到的“刻意制造陷阱让技术债务爆发”、“跨模型借用理论（Gemini 提概念，DeepSeek 去执行）”、“AI 是判例驱动的”，都是极度硬核且真实的 AI 协作经验。
针对你的文章和课程设计，作为读者和同样在探索 AI 协作的开发者，我有以下几点建议和延伸思考，供你参考：
一、 关于课程设计的建议（产品化视角）
你提到课时设计是“拉出一个技术债务严重的项目 -> 演示治理一两个问题 -> 学生实操 -> 验收”。这个闭环很好，但为了增强课程的“可交付性”和“复购率”，可以考虑以下优化：
提供“债务可视化”工具/标准：
人类程序员对“混乱”的感知是直觉，但课程需要量化。在让学生实操前，能否提供一套 AI 时代的“代码坏味道”检查清单？比如：
幻觉依赖：引入了根本不存在的库。
越权实现：UI 层写了业务逻辑（违反你提到的 Clean Architecture）。
散弹枪修改：改一个功能需要动 10 个文件。
让学生先学会用 AI 去评估技术债务（Prompt: ”请基于 Clean Architecture 评估当前代码的耦合度“），再治理。
将“反思”模板化、Prompt 化：
你提到核心习惯是“停下来让 AI 反思”。这个动作需要固化成标准的 Prompt 模板发给学生。比如：
漂移反思 Prompt：”回顾你刚才生成的代码，对比我们初始的架构约定，你在哪里发生了漂移？为什么会产生这种漂移？请给出重构建议。“
意图反思 Prompt：”我要求你引入 XXX 框架，请反思这个框架解决了当前代码的什么核心痛点？如果不引入，后续扩展会在哪里卡住？“
把这些 Prompt 做成课程的“实体交付物”，学生会觉得物超所值。
验收环节引入“AI 对抗”：
人工验收学生治理后的代码太累。可以让学生把代码交给另一个 AI（或者另一个设定为“严苛 Code Reviewer”的 Agent），如果 Reviewer AI 找不到架构违规的地方，就算验收通过。这能极大增加课程的趣味性和闭环感。
二、 对文章观点的延伸思考（理论视角）
Vibe Coding 时代的重构，本质是“重构上下文”
在古法编程时代，重构是修改代码结构；在 Vibe Coding 时代，代码只是表象，真正的技术债务是“上下文债务”。AI 为什么会乱搞？是因为上下文窗口里混入了奇奇怪怪的范例，或者丢失了最初的架构约束。
因此，你引入框架的做法极其高明——框架不是限制 AI，而是为 AI 提供最坚固的上下文护栏。只要在框架内，AI 的幻觉就被锁死了。
从“判例驱动”到“宪法编程”
你提到 AI 是判例驱动的，这非常准确。但优质的范例需要极高的维护成本。更进阶的做法是宪法编程：给 AI 制定几条不可违背的“宪法条款”（如：所有数据流必须经过 ViewModel、禁止在组件内直接调用 API 等）。一旦 AI 违宪，直接打回。这比单纯给范例更灵活，也是你所说的“封装成 Skill”的底层逻辑。
多模型协作：上帝视角与打工视角的分离
你用 Gemini 提供理论，用 DeepSeek 执行，这个经验太宝贵了！这其实暗合了目前前沿的 Multi-Agent 架构。
大模型（如 Gemini/GPT-4）充当 Architect（架构师），负责提供高维理论和审查方向。
代码模型（如 DeepSeek/Cursor）充当 Coder（码农），负责填坑实现。
在课程中，你可以把这种“狐假虎威”的调教技巧作为进阶课时教给学生，让他们学会如何在 AI 面前建立自己的“架构权威”。
三、 对文章文本的微调建议
如果这篇文章要作为课程的宣发推文，可以考虑在结构上做一点微调，让非技术读者或初学者也能瞬间 get 到痛点：
开头可以更抓人：可以先描述一个极其普遍的场景——“昨天还跑得好好的项目，今天让 AI 加了个按钮，整个系统就崩了。看 AI 刚写的代码，就像看一团乱麻，根本不知道从哪改起。” 这就是 Vibe Coding 的痛点，直接引出重构的必要性。
强化“种树”的比喻：你提到“这种编程范式很像种树”，这个比喻极美。可以再展开半句：“Vibe Coding 就像给树施了疯长肥，一天长高七米，但如果不加修剪（重构）、不搭架子（引入框架），风一吹就倒了。程序员不再是挖坑种树的人，而是修剪枝叶的园丁。”
总结：你把“被动承受 AI 制造的混乱”转化为了“主动利用混乱来训练 AI 和程序员”的思路，这不仅是 Vibe Coding 时代的必备技能，更是一种全新的软件工程哲学。这个课程方向切中了当下所有 AI 开发者的命门，非常期待它的落地！
